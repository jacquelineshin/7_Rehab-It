Section 6 - APIs

How are we planning on creating an API for our project?
- We made our API views in rehab/apiViews.py and they use JsonResponse to return data as JSON.
- /api/exercises/ is a function based view and /api/workoutSessions/ is a class based view.
- Filtering is done with query parameters using request.GET. For exercises you can filter by name, difficulty,
  minDifficulty and maxDifficulty. For workout sessions you can filter by completed and exercise.
- We also made /api/httpResponse/ and /api/jsonResponse/ to compare HttpResponse and JsonResponse. They return the
  same data but HttpResponse has the content type text/html and JsonResponse has application/json. When you open the
  JsonResponse one in Chrome it shows a pretty print option since it knows it's JSON, but the HttpResponse one just
  shows up as plain text on a page.

What kind of data are we planning to serve?
- Exercises (name, description, difficulty) and workout sessions (name, date, completed, and the exercises in it).
- We didn't include user or evaluation data since that has people's injury info and the API is public.

2: If Rehab-It grew to 10,000 daily users, I would lean toward using an external API for more complex AI tasks rather than relying entirely on a locally hosted model. While local models eliminate per-token fees, supporting that many users would require substantial computing resources, especially when multiple people are requesting recommendations simultaneously. Django could still manage user accounts, exercise information, and training plans, while the API would handle AI-generated responses. To estimate the costs, I assumed each user makes five AI requests per day, averaging 500 input tokens and 300 output tokens per request. With these assumptions we calculated monthly requests = 1,500,000; monthly input tokens= 750 million; monthly output tokens = 450 million.
Using GPT-4.1 mini as an example, at $0.40 per million input tokens and $1.60 per million output tokens, the estimated API cost would be $1,020 per month.
In comparison, an AWS server with an NVIDIA A10G GPU costs approximately $734 per month if running continuously. However, one GPU may not be enough to handle all requests efficiently. Two servers would cost approximately $1,468 monthly, excluding additional infrastructure and maintenance. I think an API would initially make more sense for Rehab-It because it could handle changes in demand without requiring us to manage expensive GPU infrastructure. However, if usage became consistently high, local hosting could eventually become more cost-effective.

3: I think a hybrid approach would be a good fit for Rehab-It because not every feature requires a powerful AI model. A smaller Hugging Face model could handle simpler requests, while an external API could be used when more detailed reasoning or personalization is needed. For example, if someone wanted beginner-friendly leg exercises, a local model could interpret the request and identify appropriate exercises from our database. However, if someone wanted a personalized training plan based on their recovery stage, physical limitations, and available equipment, an API could help organize a more detailed recommendation.
Examples of tasks and what approach they should use: Filtering exercises by difficulty - django database (does not require AI); understanding basic exercise preferences - local model (relatively simple task); generating personalized training plans - external API (requires more complex reasoning); explaining exercise modifications - verified exercise content with AI assistance (accuracy is important); tracking completed workouts - Django database (No AI needed)
This would allow us to reserve API calls for situations where they actually improve the user experience. We could also save frequently requested exercise explanations to avoid repeatedly generating the same responses. Since Rehab-It focuses on rehabilitation, I also think it is important that both models rely on reliable exercise information rather than generating recommendations without appropriate safeguards. Overall, combining local processing with an API could help us control costs without sacrificing the quality of more personalized features.
